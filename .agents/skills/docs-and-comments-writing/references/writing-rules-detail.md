# 文档与注释写作详细规则与参考表

本参考文档沉淀自本项目的 AI 写作规范（原规范来源最近核对日期：`2026-10-06`，已于 `2026-11-25` 完整内化至本仓库，不依赖外部本地路径）。日常简短任务直接按 [../SKILL.md](../SKILL.md) 执行；长文修订、词义拿捏、示例对照或规范复核时按需读取本文件。

## 1. 事实强度、读者与作者声音

- **先确认写作目标**：读者背景、用途、核心问题、语言和不可改动项。面向新手补齐必要前提与首次术语解释；面向熟悉本项目的开发者省去常识复述，直写新问题、前提与取舍。
- **事实强度不可升级**：
  - “观察到相关性”不能改写为“导致”；“可能”不能改写为“必然”；“支持某场景”不能改写为“全面支持”。
  - 数字、单位、日期、版本、平台、样本条件必须与依据一致；核验日期、样本时间等技术日期按需保留。
  - 需要限定时写具体条件（如“在 `src/component/logical_time` 单测中”），避免满篇“某种程度上”“可能也许”。
  - 来源紧邻它支持的断言；引述保留原意和措辞，改写明确为转述。
- **保留作者声音**：
  - 保留已有文稿中有依据的判断、取舍、怀疑与适度第一人称（例如“这个接口让我不敢直接用于批量删除”不自动软化成“仍有进一步优化空间”）。
  - 需要校准个人风格时，可抽样参考作者指定的 2–3 篇同类文章，只提炼背景详略、举例方式与判断直接度，不抄固定口头禅，也不移植旧文事实。
  - 没有样本时保持克制、准确、易读，不伪造作者经历。

## 2. 结构、标题与复句辨析

### 2.1 按文本类型选择自然顺序

| 文本类型 | 常见有效顺序 | 常见失误 |
| --- | --- | --- |
| 决策、选型、设计规范 | 判断或行动 → 依据 → 条件与代价 | 冗长铺垫背景，结论藏在文末 |
| 教程、操作手册 | 目标与前提 → 具体步骤 → 预期结果 → 必要排错 | 漏掉前提，或在每步反复解释背景 |
| 排障、实验复盘 | 现象 → 证据 → 排除过程 → 根因 → 验证 | 把事后推断写成当时已知结论 |
| 原理推导、学习笔记 | 问题 → 必要概念 → 推导过程 → 适用条件 | 强行结论前置打断理解链条 |
| 技术文章、博客、评论 | 随论点、观察和叙事推进 | 机械套用“背景/优势/挑战/展望” |

### 2.2 标题与入口文案规则

- 标题使用简短、正式的主题词或明确动作与对象，去掉无信息形容词和句末句号；条件与细节放在正文，不靠双分句或强制换行撑大标题。
- 正式说明与产品页面不使用口语邀约或抽象标语（如把“看一眼配置”改为“检查配置”，“看清任务，掌握处理进度”改为“任务列表与进度”）。
- **禁用口号句式**：标题和宣传文案禁用“从……到……”（及英文 `From … to …`），标题禁用“先……再……”（及英文 `First … then …`），也不换皮成“由……走向……”。正文中的真实时序（“先关闭连接，再释放缓冲区”）和范围（“从第 2 行读取到第 8 行”）正常保留。
- **入口一致性**：链接和按钮名称与目标页面或实际动作一致（指向“快速上手”就统一叫“快速上手”，不轮换“第一次使用”等说法）；下载、查看、预览、提交不互换。同一组相邻选项中，目标与操作完全相同的入口合并，确有不同用途时写明差异；修改标题时注意保护已有锚点与稳定链接。

### 2.3 汉语复句语义辨析

| 表达形式 | 关系类型 | 语义复核要点 |
| --- | --- | --- |
| `既 A，又 B` | 并列（平列） | A 与 B 同成立，分述两个方面 |
| `不是 A，而是 B` | 并列（对举） | 否定 A、确认 B；仅在纠正真实误解、区分易混概念或说明排除范围时保留，不凭空树靶子 |
| `A，但 B` | 转折 | A 仍成立，B 说明与预期不同之处或对 A 的限制 |
| `不仅 A，而且 B` | 递进 | A 仍成立并在此基础上加强 B；简化为平述时必须保留 A、B 两项事实，不可与对举混用 |

### 2.4 句子可读性检查表

| 问题类型 | 有问题的表达 | 调整方向 |
| --- | --- | --- |
| 动作被名词掩盖 | 对缓存失效进行处理 | 写出真实动作，如“删除过期缓存”（先核对源码） |
| 施事不明 | 将会被进行检查 | 指明主体与动作，如“服务端校验请求参数” |
| 多层定语 | 对用于支持……的机制所产生的…… | 先命名对象，再用下一句交代条件或作用 |
| 指代不明 | 这进一步提升了它的能力 | 写明“这”“它”的具体对象；无实义则删除 |
| 能力对象不明 | 复杂需求，直接表达 | 写明支持的结构、输入或操作 |
| 流程描述空泛 | 多项功能在一条清晰的流程里协作 | 写明职责分工、输入输出与调用顺序 |
| 虚假因果或长链 | 通过……实现……从而……确保…… | 逐项核对因果；无法证明的分别陈述，不把预期写成保证 |
| 无必要否定对比 | 本节不是罗列功能，而是介绍配置步骤 | 直接写“本节介绍配置步骤” |
| 凭空拔高对照 | 这不是普通工具，而是管理哲学 | 按实际能力重写，不留空泛后项 |
| 否定范围不清 | 不一定全部不会重试 | 写清哪些请求重试、何时停止 |
| 语气替代论证 | 显然，这种设计更合理 | 写出比较维度、条件与理由 |
| 句尾空泛拔高 | ……从而赋能效率提升 | 写具体结果，无新信息即句终 |
| 英文过度名词化 | `perform an examination of the input` | 改具体动词如 `validate the input`（按实际行为选词） |
| 英文分词堆叠 | `…, enabling …, ensuring …, highlighting …` | 拆清主语与逻辑，只留有依据的结果 |

## 3. 用词复核表（按语义判断，禁止全局替换）

### 3.1 高频中文易空泛或易歧义词（24 项）

| 词语或表达 | 含义空泛时如何具体化 | 必须保留或区分的语境 |
| --- | --- | --- |
| 补强 | 写清修复什么、新增哪项校验或补充什么测试 | 不拿一词包办多种修改 |
| 投影 | 按对象写缓存、副本或派生视图 | 数学投影、数据库投影、图形投影等准确术语保留 |
| 水位 | 写最大值、阈值、已处理序号或当前占用量 | 流处理 watermark 等明确定义的术语保留 |
| 预算 | 写重试次数上限、剩余次数、超时时长或剩余时间 | 财务预算、SRE 错误预算、明确约定的资源预算保留 |
| 终态、终值 | 状态机写结束状态及合法转移；数据写最终值/最终快照；事务写最终决议；展开“终态一次”等缩略语 | 自动机理论“终态”、`isTerminal` 等标识符保留；“结束”含成功/失败/取消，不等同成功 |
| 合同 | 研发文档中写设计规范、接口约定、字段规则、平台协议或验收标准 | 法律合同、引文和代码标识符保留原词 |
| 缺证、待证、未证 | 写明缺少什么或未完成什么（如“缺少真实样本”“本地格式尚未核验”） | 区分“尚未验证”“缺少样本”“验证未通过”，不能将“未验证”写成“不支持” |
| 证据（研发说明） | 按实际写源码依据、文档依据、样本、日志、测试结果、测量结果或验证记录 | 法律/取证语境保留；源码核验、合成测试与真实验收不能互相替代 |
| 门槛 | 写前置条件、采用条件、版本要求、验收标准、判定阈值或限制；有数值写清比较方向 | 保留“必须满足”与“参考起点”的区别；说明实际进入难度时可保留 |
| 赋能、加持 | 写清让谁能执行什么具体操作 | 引文或特定文体按需保留 |
| 抓手、底座 | 写方法、工具、公共库、运行时或基础服务 | 说明具体对象与职责 |
| 打通、链路 | 写连接对象、数据流向与调用顺序 | 网络链路、链路追踪等准确术语保留 |
| 沉淀、落地 | 写记录结论、持久化数据、抽取公共代码、实现或部署 | 实现、部署、持久化不能混称 |
| 闭环 | 写明具体步骤和完成条件 | 闭环控制等工程概念保留 |
| 对齐、拉齐 | 写按什么规则修改、哪些字段须一致 | 内存对齐、序列对齐、模型对齐等准确术语保留 |
| 收敛 | 写合并、统一状态或缩小范围 | 算法收敛、状态收敛等特定概念保留 |
| 口径 | 写计算规则、统计范围或时间来源 | 涉及多套规则时分别说明 |
| 维度、颗粒度 | 写指标、条件或处理单位（如“按批次处理”） | 张量维度、空间维度等准确术语保留 |
| 兜底 | 写触发条件与实际动作：重试、默认值、拒绝或清理 | 不同动作不可互相替换 |
| 护栏、门禁 | 写参数校验、权限检查、发布前检查及阻断条件 | 安全工程等已定义专有概念保留 |
| 钳制 | 写数值上下限及超限处理方式 | 控制、电路、数值计算术语保留 |

| 夹具 | 测试静态数据文件写测试数据、样本或样本文件 | 泛指 xUnit 固定测试前提时保留英文 `fixture` 或项目既有约定 |

### 3.2 空泛修饰与套话处理

| 表达 | 处理原则 |
| --- | --- |
| 值得注意的是、需要指出的是、事实上 | 删去不损失真实提醒或转折时直接陈述 |
| 显然、不难发现、毋庸置疑 | 改为具体理由或依据 |
| 本质上、从某种意义上说、从某个角度来看 | 说明具体机制、范围或视角，否则删去 |
| 全面、全方位、深度、系统性 | 列出实际覆盖范围或方法；无法证实完整性时不用 |
| 无缝、开箱即用、强大、优雅、高效、稳健 | 写前提、能力、限制或实测结果；无实测不编造性能数据 |
| 本文将深入探讨、接下来让我们、`Let's dive in` | 删除纯预告句；保留有助于选读的范围与前提说明 |
| 问题来了、答案很简单 | 连续论述直接解释；FAQ/排障中的真实问题按需保留 |
| 只需、轻松、一站式、`simply` | 写实际前提、动作与支持范围；表示精确排他条件的“只”/`only` 保留 |
| 业界普遍认为、研究表明 | 写明具体来源、研究对象和适用范围 |
| 综上所述、总而言之、归根结底、`Ultimately` | 保留能导出结论、取舍或下一步行动的小结，删除换词复述 |
| 对……进行……处理、开展……工作 | 换成准确动词：加载、校验、删除、比较等 |

### 3.3 英文与双语规则

- `delve`、`leverage`、`robust`、`seamless`、`pivotal`、`comprehensive`、`tapestry` 按语义与上下文复核，不机械替换；`serves as`/`acts as` 仅在确实描述角色时使用。
- 英文同样避免无信息的 `not X but Y` / `It's not X, it's Y`；简化 `not only X but also Y` 时保留两项事实；正常转折词 `but`/`however`/`yet` 按语义保留。
- 双语文档按各自语言自然语序重写，不生硬直译英语被动句或长名词串；同一概念在全篇固定使用同一术语。标点（破折号、分号、括号等）按语法用途使用，不因模型常见就机械禁用。

## 4. 代码相关文本保护表与技术语义核对

| 文本类型 | 重点写清 | 润色时必须保护 |
| --- | --- | --- |
| 代码注释 | 原因、不变量、边界、顺序要求、设计权衡 | 与当前实现一致，不复述显而易见的操作 |
| 文档注释 / 接口文档 | 参数及单位、返回值、错误、前置条件、副作用、并发/所有权/取消语义 | 文档标签、类型、签名、契约强度、运行时读取字符串 |
| README / 教程 | 目标、依赖、步骤、预期结果与必要排错 | 命令、路径、版本条件与真实可执行性 |
| PR / 变更说明 / Commit | 触发问题、行为变化、影响范围与验证结果 | 不把局部修复写成全面解决，不把未跑测试写成通过 |
| 日志 / 错误消息 / 界面文案 | 实际发生了什么及用户可采取的行动 | 错误码、模板变量、日志解析格式、快照、监控规则、i18n 键 |

**技术语义最低核对清单**：

1. 次数定义：总尝试次数还是首次失败后的重试次数；何时递增、何时重置。
2. 时间定义：截止时刻还是持续时长；单位与时间来源（如本仓库 `logical_time` 逻辑时间 vs 系统时间）。
3. 数值边界：区间是否含端点；缺省值、空值（`nil`）与零值是否等价。
4. 数据形态：缓存、独立深拷贝（如 `proto.Clone()`）还是实时派生视图；刷新是否存在延迟。
5. 失败行为：重试、忽略、回退默认值、报错返回还是终止；是否已产生副作用。
6. 执行阶段：阻塞还是异步；完成、成功、提交、持久化与收到响应是否分属不同阶段。
7. 验证类型：源码核验、文档核验、单测/合成测试、真实样本还是线上运行；结论不得越界。

## 5. 正反改写与保留示例（教学假设示例）

> 以下示例仅说明表达规则，不代表 `atsf4g-go` 真实接口或实测结果；实际改稿前须核对对应源码。

- **动作与边界可见**：
  - 原句：`通过补强超时兜底链路，全面赋能系统稳定性。`
  - 若实现仅做超时清理：`请求超时后，服务会清理等待队列中的对应记录。`
- **数量表达不可近义替换**：
  - 约定“总尝试次数最多 3 次（含首次）”时，不写“最多重试 3 次”，应写：`总共最多尝试 3 次；首次调用失败后，最多再重试 2 次。`
- **无必要否定对比直接写结论**：
  - `本节不是罗列功能，而是介绍配置步骤。` → `本节介绍配置步骤。`
  - 需纠正误解时保留：`这里统计的不是请求次数，而是消息条数。`
- **研发状态准确表达**：
  - `源码证据不能代替桌面证据。` → `源码核验不能代替原生桌面验收。`
  - `MCP 采用门槛。` → `MCP 采用条件。`
- **应当保留的正常表达（不得因命中词表误改）**：
  - `训练损失尚未收敛。`（算法性质）
  - `这个接口返回视图，不复制数据。`（真实语义区分）
  - `先关闭连接，再释放缓冲区。`（正文中的真实操作顺序）
  - `错误预算已用完。`（已定义的 SRE 术语）
  - `重复确认目标目录后再删除。`（高风险操作的必要提醒）

- **预印本（待继续跟踪正式发表）**：`arXiv:2604.22142v1`（2026-04-24，保留声音提示的边界）、`arXiv:2603.18161v2`（2026-08-26，语法编辑仍可能引起语义漂移）、`arXiv:2608.26710v1`（2026-08-27，编辑对不同 AI 检测器评分方向不一致）、`arXiv:2608.27855v2`（2026-09-22，生成与编辑文体特征不同）。
- **官方编辑指南与社区参考**：Google Developer Style（Voice and tone，2026-05-27）、Microsoft Style Guide（Simple words / Avoid jargon / Headings，2022-06-24）、GOV.UK Functional Standards writing style guide（2024-09-30）、Wikipedia Signs of AI writing（社区线索参考，非正式政策或禁词表）。
- **当前验证边界**：以上研究与指南已按摘要/公开版核对，但尚未在本仓库开展多模型对照写作实验或读者盲评；评估写作质量以“读者能否复述核心意思、依据是否充分、下一步操作是否明确”为准，不以单一 AI 检测分数或句长波动替代人工复核。

### 6.3 规范后续复核与更新方法

- **复核周期**：建议每 3–6 个月，或主力模型切换、反复出现语义漂移、新增文体时复核一次。
- **评估与更新**：选取 12–20 条涵盖中文、英文、Go 注释、接口说明与技术文档的代表性样本（含易误伤的正常表达），在同一模型与可比设置下盲评新旧规则，先验事实与语义保真再评文风；出现语义退化时优先回退或收紧候选规则。更新时同步 `SKILL.md` 与本参考表，正文只保留当前有效规则，变更历史交由 Git 追踪。
