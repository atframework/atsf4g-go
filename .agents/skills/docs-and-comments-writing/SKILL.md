# 工作结果

产出准确、自然、语义无漂移且符合本仓库约束的注释或文档修改，涵盖：

- Go 源码注释、导出声明文档注释（兼顾 `.golangci.yaml` 中 `godot` 与 `misspell` 规则）、错误消息与日志说明。
- `doc/docs/` 下 MkDocs 文档、协议说明、架构文档、README、PR/变更说明与技术方案。
- 修改后保持所有技术事实、边界条件、标识符、路径、链接和验证状态与源码或实际运行结果一致。

## 适用范围与输入

- **适用场景**：新写或润色代码注释、文档字符串、接口说明、README、变更说明、技术报告、MkDocs 页面及中英双语技术说明。
- **不适用场景**：修改代码业务逻辑、修复功能缺陷、执行 `goimports`/`clang-format` 等机械格式化，或仅按字数/AI 检测器分数改稿。
- **必要输入与前提**：
  - 待修改文本（或写作主题）及其直接关联的源码、proto 定义、配置键、测试或图表。
  - 目标读者、用途、语言（中文为主或英文）以及不可改动的技术契约。
  - 若事实、行为或验证结果缺失，先读取对应源码、配置或运行记录核实；不得编造数字、来源、实验结果或代码行为。

## 工作流

1. **界定目标与保护项**
   - 明确读者、文本类型、语言和修改范围；局部问题只改有问题段落，不重写无问题全文。
   - 标记不可被润色改变的内容：标识符、配置键、环境变量、路径、错误码、协议原文、数值范围与端点开闭、单位、时间来源、否定与条件、情态强度（必须/应当/建议/可以）、验证状态及原始命令输出。
   - 改写已有文本时，按 **事实 → 论证 → 结构 → 语法 → 措辞** 的顺序处理。

2. **核对事实并组织结构**
   - 先核对源码、配置、命令或一手资料，严格区分“已验证事实”“推断”与“未知/未验证”。
   - 按文本任务选择自然顺序（决策说明可结论前置，教程按目标→前提→步骤→结果→排错，排障按现象→证据→排除→根因→验证，原理推导保留过程）；材料只有两点就写两点，不强凑三点、等长小节或每节重复小结。
   - 连续论证用自然段，步骤与并列项用列表，字段映射或对比用表格；删除不推进内容的寒暄、空泛预告和对话包装。

3. **落实清晰句式、标题与精确用词**
   - **具体对象与准确动词**：写清谁在什么条件下做什么、结果是什么；不靠“清晰”“可靠”“无缝”“优雅”“高效”等修饰代替机制说明。无性能实测时不编造数字，可写经源码确认的机制。
   - **术语一致**：同一概念固定使用同一名称，不为变换措辞轮换“缓存/副本/视图/投影”等不同语义词；专业术语准确时直接保留。
   - **标题与入口文案**：标题简短、正式、具体，不带句末句号，不用口语邀约或抽象感受；**标题和宣传文案禁用“从……到……”式覆盖口号，标题禁用“先……再……”句式**（正文中的真实操作时序和数值范围正常保留）。链接与按钮名称与目标页或动作一致，不重复堆叠指向同一目标与操作的冗余入口。
   - **克制装饰性修辞**：少用“不是 A，而是 B”等先否定再肯定句式——否定项不增加信息时直接写结论，纠正误解、区分概念或说明排除范围时保留；简化“不仅……而且……”时保留两项事实；转折与递进按真实逻辑使用，不设词频禁令。
   - **按语义复核高频空泛词**：遇到“补强、兜底、赋能、闭环、落地、沉淀、打通、链路、抓手、底座、缺证、证据、门槛、终态、合同、水位、预算、投影、夹具”或英文 `delve/leverage/robust/seamless/comprehensive` 等词，先判断是否准确术语再决定展开或保留，**禁止机械禁词表全局替换**（详表见按需资源）。
   - **保留作者声音**：保留作者有依据的立场、判断、取舍与适度第一人称，不强行中性化，也不凭空编造个人经历、口头禅或故意引入错字/随机句长。

4. **保护本仓库代码与文档契约**
   - **Go 注释**：解释不易从代码看出的原因、不变量、并发/所有权边界与顺序要求，不逐行复述明显操作；遵循 `.golangci.yaml`（`godot` 要求声明注释英文句末标点与首字母规范、`misspell` 美式拼写、行长 150 列约束）。
   - **接口/日志/错误文本**：保护错误码、模板占位符、监控解析字段与兼容性要求；明确说明发生了什么及调用方可采取的动作。
   - **MkDocs 文档**：遵守 `doc/docs/writing-guide/index.md`（相对路径资源、按场景选用 Mermaid/Draw.io/Excalidraw、标题层级递增、图表在展示尺寸下文字可读且标注截图/快照/示意图区别）。
   - **发现代码或契约本身有误时**：单独记录并作为功能/设计问题处理，不夹带在纯文风修订中静默修改。

5. **通读复核与交付**
   - 对照修改前后逐项核对：否定、数量、单位、端点包含性、重试次数定义（总次数 vs 失败后重试次数）、截止时刻 vs 持续时长、阻塞/异步阶段、验证状态是否完全保真。
   - 检查全文重复模式（重复句首、密集对偶、机械三段式、冗余小结、助手寒暄）。
   - 后续润色不再带来可说明的改进或开始损伤语义/作者声音时停止修改。

## 异常与恢复

- **材料或源码依据不足**：先写出有依据的部分并列出待确认问题，将未查证处明确标为“尚未验证”或“缺少样本”，禁止脑补细节。
- **润色引发技术语义漂移**：立即回退受影响段落，恢复原技术限定词、阈值方向与代码标识符，优先保证准确性而非辞藻流畅。
- **既有文档与源码实现冲突**：保留冲突记录，以实际源码和配置为准修正或标注差异，不顺手修改无关模块代码。
- **需要周期性复核规范本身**：参考按需资源中的研究边界与对照评估方法（建议每 3–6 个月或主力写作模型更换时复核），只合并经代表性样本验证的规则改动。

## 验证与交付

- **静态检查**：
  - 核对所有引用文件路径、内部锚点、代码块语言标记与围栏闭合。
  - 若修改了 Go 注释，运行对应模块编译/检查（如 `go vet ./...`，或具备条件时运行 `golangci-lint`）确认未破坏注释语法、`godot`/`misspell` 或 `//go:` 指令。
  - 若修改了 `doc/docs/` 页面，检查相对资源路径与图表语法；如本地已准备 `doc/pyvenv`，可用 `task "fast-[doc]-build"` 验证 MkDocs 构建，未运行则明确标注“文档构建未运行”。
- **交付说明**：列出修改文件、关键语义保护点、实际执行的检查结果以及未运行的检查项；交付正文中不混入助手寒暄或编辑过程批注。
